## 1. Project overview

**Organization.** Project Tomorrow (tomorrow.org) runs the annual **Speak Up** survey. Agile-Ed hosts and develops the system. Bob is the technical owner and also manages DNS for tomorrow.org directly. "Michelle" is the Speak Up manager on the staff side (referenced in the plan).

**Speak Up (the app).** An ASP.NET Web Forms "Web Site" project (no .csproj, only a .sln with a website entry), continuously upgraded over many years. It contains:

- **Survey taking** – what respondents (students, parents, educators, community members) use. Reached by short links that identify the school/district and the survey.
- **Staff admin** – reporting, configuration, survey building (Telerik UI for ASP.NET AJAX is used on the admin/reporting pages, **not** on the survey pages).
- **District/school results** – reports districts and schools reach for their own results.
- **Past-year results** – the oldest code and data structures; Bob calls it the biggest security risk and expects it to be a headache.

**SurveyBank.** The question bank database (surveys, questions, options). The survey taker reads survey definitions from SurveyBank (stored proc `GetSurveyToTake` lives in the SurveyBank DB). A "surveybank development" component (building surveys/questions) is planned to move into the new admin site, likely in 2027.

**Usage (2025-26 log, ~311k rows, 2025-07-22 to 2026-09-25).** Season runs through spring:

| Path | Starts |
|---|---|
| S/D short links (SchoolStart/DistrictStart "DirectStart") | ~113,400 (main path) |
| Q quick start (QuickSurveyStart) | ~17,500, almost all survey 195 in June 2026 (org 73021 / reg 252487) |
| Register flow | ~210 |
| SID.aspx / SIDstart | ~250 log entries |
| LookupBuilding | ~500 debug entries |

Monthly: small in Sep–Oct, **Dec peak (17k)**, Jan–Feb quiet, **Mar 16k, Apr 40k, May 32k**, Q in June. October is the start of the season, not the busy part. Most-started surveys: 169, 170, 172, 171, 117, 120, 153, 119, 155, 152. (The log is event-based, not a complete page-hit record.)

**Naming convention (Bob's).** `speakup2025` = the 2025-26 season; `speakup2026` = the 2026-27 season. (My early examples used survey-2026/2027; Bob's naming prevails.)

## 2. Target architecture and why

**.NET version – [DECIDED]:** .NET 10 (LTS).

**Migration strategy – [DECIDED]:** strangler-fig, side by side. Each component becomes its own new app on its own subdomain; the old Web Forms code stays running as the fallback and the home for everything not yet migrated. Only **active** code is migrated; goal is to cut the codebase by more than 50%.

**Why leave Web Forms at all.** ASP.NET Core does not support Web Forms. .NET Framework 4.8 has no fixed end of support (tied to the Windows OS lifecycle), so staying was a legitimate option, but Bob chose to migrate because Agile-Ed is moving fully to Azure and wants the app to live there. Bob is also aware he will rely heavily on Claude for .NET Core troubleshooting.

**Options considered and not chosen:**

- Keep everything in Web Forms for another 5–10 years. Not chosen (see above).
- Bridge libraries (e.g., CoreForms) to run Web Forms-style code on Core. Discussed; not chosen.
- **Containerizing the current Web Forms site first** (a senior engineer's suggestion, not a requirement) to get to Azure early. **Explicitly rejected**: Bob chose to build the new .NET Core survey taker on the existing VM, designed to move to Azure later, calling that "much preferable".
- Moving DNS to Cloudflare before October launch. Rejected for now (see section 3).
- Converting page by page inside one app. Not possible in Web Forms → Core; hence the per-subdomain approach.

**Hosting – [DECIDED] for now:** the existing Windows Server 2019 VM with IIS + the .NET 10 Hosting Bundle (installed; `AspNetCoreModuleV2` confirmed present in IIS Modules). Existing SQL Server on a separate Windows Server 2019 VM (10.0.8.23); SQL login authentication. Web server internal IP is 10.0.8.24 (firewall/NAT forwards the public IP to it). Not containerized. **Azure later**, with the database moving at the same time.

**Azure-ready rules – [DECIDED]:** stateless (no session state; every page loads from the DB using the taken-survey ID); settings from config/environment; no local disk writes; no Windows-only APIs; no new cross-database queries or SQL Agent dependencies. The survey taker does **not** depend on a shared API.

**Auth – survey taker [DECIDED]:** none for respondents. They are anonymous, identified only by the link code in the short URL and the taken-survey ID (TSI) afterward. Staff/district sign-in (Entra ID? how districts sign in today?) is **[OPEN]** and only matters for later phases.

**Data access – [DECIDED]:** call the **same stored procedures with the same parameters**. No schema changes to `users_surveys` or the answer tables. **[RECOMMENDED]:** `Microsoft.Data.SqlClient` with thin hand-written data classes (or Dapper) wrapping each proc; no EF Core, since the stored procedures are the contract. The new app's writes must be indistinguishable from the old app's. The stored procs hide the temp-database / main-database split (see section 4).

**UI framework – [OPEN / RECOMMENDED]:** the staff spec says "ASP.NET Core (Razor / MVC)". Bob has not chosen between Razor Pages, MVC, Blazor, or API+SPA. **My recommendation:** server-rendered Razor Pages (or MVC) with minimal JavaScript, one POST per page, because it matches the stateless/TSI design, maps one-to-one to the existing save procedures, is easy to make accessible and mobile-friendly, and the staff's own prototype is a throwaway client-side demo. Reject Blazor Server (needs a persistent connection and server-side circuit state, which conflicts with the stateless rule) and API+SPA (more moving parts than the October date allows).

**Error alerting – [DECIDED]:** no SMTP relay (it could never be made to work). Use structured logging plus a daily summary through Microsoft Graph; App Insights later on Azure.

**Why these choices, in one line each:** stateless because the old design's rebuild-from-DB logic already carries real load (11k reloads on SpeakupQuestions and 4.7k on Intro last season); same stored procs because the temp/main DB load and reporting depend on them; side-by-side because the October date is hard and the old code must stay as fallback.

## 4. Database

Two databases: **Speakup** (operational: `users_surveys`, answer tables, `Registrations`, organizations/registrants, the temp/main split) and **SurveyBank** (surveys, questions, options). SQL login `speakup` on 10.0.8.23 in production. The Speakup DB is **not** TDE-encrypted.

**Temp vs main (from Bob's notes).** Each page forward saves to a temporary database; the data stays there until late evening, when the temp DB integrity is checked and loaded into the main database, then the daily answer database is reset. `users_surveys` (survey general info) and the answer table are **write-only / never deleted** — rows are flagged "don't use" instead; deletes happen only in the temporary table. Back-navigation re-reads the answers into memory and deletes them from the temp table. The stored procs hide all of this.

|---|---|---|
| `GetMaintenanceDate`, `GetSurveyDates`, `GetDistrictOpenClose` | Speakup | Open/closed checks |
| `ChkSurveyId`, `GetOrganizationInfo`, `GetInstInDistrict`, `CheckForCustomSurveyList`, `GetSurveyTypesDist`, `GetSurveyListByTypeDist`, `GetDescriptorText`, `LogEntryPoint` | Speakup | Start pages |

### Page flow of the old code (behavior to match)

1. **S.aspx** (`/S/{linkcode}/{surveyid}`) or **D.aspx** (`/D/{linkcode}/{surveyid?}`): strips anything after `?` (links rewritten by Facebook and others), splits the path, puts parts in Session, redirects to SchoolStart / DistrictStart. S: school link code (a random 4-character code per school/district) + survey id. D: district code, optional school code, optional survey id. (Q.aspx `/Q/{surveyid}` → QuickSurveyStart, deferred; it uses a dedicated organizations/registrants record that accepts all Q surveys.)
2. **SchoolStart / DistrictStart** checks, in order: maintenance window (`GetMaintenanceDate`); season open — date between OpenDate and DistrictCloseDate (`GetSurveyDates @site = SUcodes.Sites.SurveyYear`); link code valid (`SELECT … FROM Registrations WHERE LinkCode = @linkcode`; DistrictStart uses `GetOrganizationInfo`); district open/close (`GetDistrictOpenClose`, status flag or dates, optional custom closed message); survey ID valid (`ChkSurveyId`). Shows a confirmation view (district, school, survey) in English or Spanish. On confirm: `GetSurveyDesc` (SurveyBank), then `StartNewSurvey` (org, reg, survey, name, title "Speak Up " + TextYear, type, quesperpage = 5, IP) → **taken_survey_id**; sets cookie `ProjectTomorrowSurvey` = taken_survey_id (3 hours); redirects to `SpeakupIntro.aspx?TSI={id}`.
3. **SpeakupIntro:** reads `surveys` in SurveyBank (title, name, GroupSurvey, intro, total_questions); shows intro and "The survey consists of N questions". Next: group surveys → SpeakupGrpStrt; all others → `SpeakupQuestions.aspx?TSI=`.
4. **SpeakupGrpStrt** (group surveys only): asks the number surveyed, must be 2–999 (message says "less than 1000"); saves with `UpdateK2GrpCnt`; goes to SpeakupQuestions. (Bob's notes say the group count is asked on Intro; the code does it on GrpStrt.)
5. **SpeakupQuestions:** five questions per page in the old code; page numbers computed from `question_sort` so a grid's sub-questions stay together. Next/Back save the current page first. After the last page: `MarkSurveyCompleted`, then `SpeakupComplete.aspx?TSI=`. Respondents may skip any question, even all of them.
6. **SpeakupComplete:** clears the session; has Michigan-teacher and Arizona-educator branches (now to be dropped); timer sends the user back to Default.

### Question types (11) and save rules to replicate exactly

Types: `checkbox`, `checkboxother`, `dropdownlist`, `grid`, `integer`, `likert`, `likertgrid` (grid_answer_type CHECK or RADIO), `radio`, `radioother`, `text` (max 4000 chars), `verticalgrid`. "Other" text boxes allow up to 2000 chars.

- Every question on the page: first `DeleteQuestion`, then one `SaveAnswer` per checked option.
- `checkboxother`: the "Other" option is saved with its text. It counts as selected when it's checked **or** when there is text in the Other box. "Other" is matched by option text: OTHER / OTRO / OTROS / OTRA / starts with "OTRA RA" (**this exact-text matching is the bug that loses answers**; fix with starts-with / flag).
- `radioother`: **if the Other box has text, only the Other option is saved and the radio selection is ignored** (open question whether to keep this).
- `integer`: one `SaveAnswer` per option **including blanks** (OptionValue left null).
- `text`: OptionId null, OptionValue = the text.
- `dropdownlist`: always saves the selected value, even the empty "Please Select".
- `verticalgrid` save calls `GetOpenEnded`, which looks for a textbox the page never creates — would crash; the type is probably unused. `GetVerticalGrid` exists but is never called.

### Group surveys (as actually coded)

For **survey 6 (K2Grp) and 55 (GrpG35)**, on page 1 only, the options of **question 110 / 471** must add up to exactly the group count or the user gets a JS alert and cannot continue. Parent and community group checks are commented out. "Each value ≤ group count" is enforced only in the browser on blur, not on the server. Bob's notes describe group surveys as: numeric entry boxes instead of radio/checkbox; individual answers ≤ the number entered at the intro; multiple answers per question allowed so the total across options can exceed the group size. Back from page 1 of K2Grp redirects to `SpeakupK2GrpStrt.aspx`, **which does not exist** (the real page is SpeakupGrpStrt).

### Spanish

Question pages switch to Spanish for survey types **FAMSPAN / STUSPAN**. "Page X of Y" and the browser-back warning are translated only for FAMSPAN. SpeakupIntro checks for "PARSPAN", which isn't a defined type, so its Next button is probably never Spanish.

## 6. Known problem areas and risks

**In the old code (details in `claude/survey-taker-current-behavior.md`):**

- **"Other" answers lost about 28,800 times** per season (exact-text match). Top questions: 3646 (3.7k), 3392, 3559, 2889, 2910, 4061, 3895, 2908, 4074, 3757. Lost text is still in the log rows (taken survey ID + question + text) so it may be recoverable.
- **web.config (committed to git) holds the SQL login password in plain text.** App uses SQL login `speakup` against 10.0.8.23. **The new app must keep secrets out of the repo** (user secrets / environment variables / Key Vault later).
- Production has `compilation debug="true"` and `customErrors mode="Off"` — detailed errors and stack traces show to users.
- **TSI is a plain integer in the URL**: anyone can change it to load or alter another person's in-progress survey (only completed surveys are blocked). Bots and link previews (Google Web Preview, Facebook, Bing, Snapchat) load survey pages with real TSI URLs (~3,500 rows). Plan intent: add a check value to the URL and mark survey pages `noindex`. **[OPEN]** exact mechanism, since TSI is the integer the stored procs take.
- **Hard-coded values:** survey IDs 6, 55, 162; question IDs 110, 471; `SUcodes.Sites.SurveyYear = "2025"` and `TextYear = "2025-26"` (season-open check and survey title) — verify what the live site actually has; `QuesPerPage.Standard` = 5.
- Each save opens/closes a connection per question and per option, no transaction. The survey cache read is commented out, so questions/options are reloaded from SurveyBank on every page load.
- Survey 162 redirects to `LookupBuildingQS.aspx`, which isn't in the project (2022 leftover). Sponsor banner code is disabled with an early `return` (2015); when it was re-enabled it produced 118 errors "Invalid object name 'SponsorBannerSurveys'" (table doesn't exist). Required-field validators are generated though surveys never require answers; the Likert validator targets a control that doesn't exist.
- Google Analytics tags are Universal Analytics (`UA-`), dead since 2023.
- Session lost mid-survey: 11k reloads on SpeakupQuestions, 4.7k on Intro; "Surveys don't match 0" 1,250 times (session lost on postback → TimedOut).
- Invalid survey IDs in links 2,225; invalid link codes 260; survey info not found on Intro 983.
- **Error emails fail** (1,166; SMTP relay never worked). Problems are found by user reports plus Bob searching the log.
- Admin side (later phases): Download Surveys CSV had 46,600 errors "Column 'survey_id' does not belong to table" (already known/fixed); ExcelReportOnly has 733 errors "Invalid column name 'QuesRepondents'" (one report's SQL is broken).

**Project risks:**

- **Hard October date** (go-live last week of October), with ~1 week of build time remaining as of Oct 8 (original build window Oct 5–16, test Oct 19–23, go live Oct 26–30). The old code stays the fallback; any unhandled short-link path must redirect to Speakup2026.
- **One question per page vs. old five per page:** `StartNewSurvey` takes `quesperpage` and `GetRestartInfo` returns QuesPerPage; unknown whether `GetSurveyToTake` with 1 works unchanged and how page numbering/grids behave. Respondents mid-survey at cutover would have a stored QuesPerPage of 5 — new app should honor the stored value on restart. **Needs the proc text.**
- The cloud sandbox Claude used for planning has no .NET SDK, cannot reach SQL (10.0.8.23) and has no working GitHub login, so all building/testing has to happen in Claude Code on Bob's machine against a **test copy** of the databases. **Never develop against production**; the new app writes real rows.
- Installing/restarting IIS affects other Agile-Ed sites on the same server.
- Visual Studio's support for .NET 10 depends on the version (VS 2026 expected); Claude Code + the `dotnet` CLI avoids this.
